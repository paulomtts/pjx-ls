# M5b: Python intelligence inside the `{#python` block — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task by task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

Date: 2026-11-26. Base: pjx-ls master `212dc66` (0.6.0). Roadmap:
`docs/plans/2026-11-26-m1-m5.md` §7. Spike: `docs/plans/notes-m5-spike.md` (read it first;
every number and choice below comes from it).

**Goal:** names inside a `{#python` block are coloured as in a `.py` file (semantic tokens),
then hover, go to definition, completion and signature help work there too.

**Architecture:** a private basedpyright language server, bundled in `dist/`, started lazily
as a child process. `src/core/` holds everything that is pure: the Python view of a
document, a small JSON-RPC client over two streams, the session that keeps the server's
documents in step, and the translation of its answers. `src/vscode/` holds one thin adapter
per feature. The view is opened in the server under the `.pjx` file's own URI with
`languageId: python`; it has the same lines and columns as the `.pjx`, so no position or
own-document location is ever translated.

**Tech stack:** TypeScript, `node --test`, esbuild, `basedpyright` 1.40.2 (npm, MIT) as a
pinned dev dependency copied into `dist/basedpyright/` at build time. No
`vscode-languageclient`, no new runtime dependency.

## Scope

- **M5a is done**: 0.6.0 writes stubs automatically (`pyjinhx.generateStubs`,
  `src/core/stub-fix.ts` `AutoStubs`, `src/vscode/stub-fix.ts`). This plan assumes a
  current `.pyi` beside every `.pjx` with a block; the spike showed sibling components
  resolve only through those stubs.
- **In:** semantic tokens (first, shipped on their own as 0.7.0), then hover, definition,
  completion with resolve, signature help (0.8.0).
- **Out:** diagnostics from the private server (decision 4), auto-import completions,
  rename, references, inlay hints, `untitled:` documents, `template = """…"""` strings in
  `.py` files (the editor's own Python server already has that file).

## Decisions for the maintainer

Each has a recommendation; the plan is written for the recommendation.

1. **Server: basedpyright, not Pyright.** Open-source Pyright has no semantic tokens
   (measured). basedpyright is MIT, has them, and is what cursorpyright is forked from.
   *Recommended: basedpyright.* No real alternative if tokens are the priority.
2. **Bundle it or require it installed?** Bundling adds 5.8 MB to the `.vsix` (0.13 MB
   today) and works for everyone; requiring `basedpyright-langserver` in the environment or
   on `PATH` adds nothing and works for almost nobody out of the box. *Recommended: bundle,
   pinned to an exact version, plus `pyjinhx.pythonBlock.serverPath` to point at another
   `langserver.index.js`.*
3. **Memory.** The second server costs about 270 MB after the first answer on the pyjinhx
   project and grows to 530 to 590 MB without a limit. *Recommended: start it with
   `--max-old-space-size=256` (379 MB resident, 111 to 118 ms per recolour, measured), start
   it only when a `.pjx` with a block is open, and offer `pyjinhx.pythonBlock.enabled`
   (default `true`) to turn the feature off.* The alternative that costs no memory is the
   shadow-file transport, rejected in the spike notes for ghost diagnostics and lag.
4. **Diagnostics from the block.** The private server pushes them (the todo example has
   one per component: `"store" is not a known attribute of "None"`), and nothing else
   checks the block today. Showing them is one small task, but they follow the project's
   `[tool.pyright]` settings and would be new squiggles in every open component.
   *Recommended: not in M5b; add later behind a setting, default off.* Until then the
   server's `publishDiagnostics` are dropped.
5. **Version drift against cursorpyright.** The bundled server (1.40.2) is newer than the
   one inside cursorpyright 1.0.13 (1.32.1); 3 minor tokens differed in the spike, none in
   colour class. *Recommended: accept, and pin; bump deliberately with the goldens.*
6. **Decided: editor tests run under Xvfb.** The maintainer installed it
   (`/usr/bin/Xvfb`, `/usr/bin/xvfb-run`). Every editor run on this machine goes through
   `xvfb-run -a` on X11, never Wayland (see Testing). Nothing left to decide here.

## Task 1: the Python view

**Files:** create `src/core/python-view.ts`, `test/core/python-view.test.ts`.

```ts
import { scan as scanText, type Scan } from "./regions.ts";

export interface PythonView {
  /** The document with everything outside the block's body blanked; same lines and columns. */
  text: string;
  /** 0-based first and last line of the body. */
  firstLine: number;
  lastLine: number;
}

/** The Python view of a .pjx text, or null when there is no closed `{#python` block to serve. */
export function pythonView(text: string, scan: Scan = scanText(text)): PythonView | null;

export const inBody = (view: PythonView, line: number) => line >= view.firstLine && line <= view.lastLine;
```

Rules: null when `scan.error` is set, when there is no block with keyword `python`, when
its `bodyLines` is null (empty body), or when the document also has a `def` block (the
roadmap's `def-with-python`). Blank with the same `replace(/[^\r\n]/g, " ")` that
`virtual-html.ts` uses, so CRs and line count survive; a leading byte order mark becomes a
blank.

## Task 2: a JSON-RPC client over two streams

**Files:** create `src/core/lsp-client.ts`, `test/core/lsp-client.test.ts`,
`test/fixtures/fake-langserver.mjs`.

```ts
import type { Readable, Writable } from "node:stream";

export interface Cancel { readonly cancelled: boolean; onCancel(listener: () => void): void }

export class LspClient {
  constructor(input: Readable, output: Writable);
  /** Rejects with the server's error, or with "closed" when the stream ends first. */
  request<T>(method: string, params: unknown, cancel?: Cancel): Promise<T>;
  notify(method: string, params: unknown): void;
  /** Answers a request the server sends; without a handler the answer is null. */
  onRequest(method: string, handler: (params: any) => unknown): void;
  onNotification(method: string, handler: (params: any) => void): void;
  /** Rejects everything pending; later calls reject at once. */
  close(): void;
}
```

Framing is `Content-Length: N\r\n\r\n` plus N bytes of UTF-8 JSON; N counts bytes, not
characters, and a message may arrive split across chunks or several in one chunk. A
cancelled request sends `$/cancelRequest {id}` and resolves `null` when the server answers
with error code `-32800`.

- [ ] **Step 1: failing tests** with two `PassThrough` streams standing in for the server:
  a response resolves the matching request by id; two responses in one chunk; one response
  split in the middle of a multi-byte character (use `"é"` in the payload); an error
  response rejects with its message; a server request (`workspace/configuration`) gets the
  handler's result back under the same id, and `null` with no handler; a notification
  reaches its handler; cancelling writes `$/cancelRequest` with the id and the `-32800`
  answer resolves `null`; `close()` and an ended input both reject what is pending.

```ts
export interface ServerProcess { stdin: Writable; stdout: Readable; kill(): void; onExit(listener: (code: number | null) => void): void }

export interface ServerOptions {
  /** Starts the server: the real one, or a fake in tests. */
  start: () => ServerProcess;
  /** Workspace folders as file URIs. */
  folders: () => { uri: string; name: string }[];
  /** The interpreter for the folder that holds `scopeUri`, if one is known. */
  pythonPath: (scopeUri: string | undefined) => Promise<string | undefined>;
  log: (line: string) => void;
}

export interface Legend { tokenTypes: string[]; tokenModifiers: string[] }

export class PythonServer {
  constructor(options: ServerOptions);
  /** Opens the view, or replaces its text if it is open; a no-op when the text is unchanged. */
  sync(uri: string, text: string): void;
  close(uri: string): void;
  /** Null when the server is not running or has no token support. */
  semanticTokens(uri: string, cancel?: Cancel): Promise<{ data: number[]; legend: Legend } | null>;
  /** A `.py` or `.pyi` changed on disk: the server does not watch files itself. */
  filesChanged(uris: string[]): void;
  /** The interpreter or the settings changed: the server asks for its configuration again. */
  configurationChanged(): void;
  /** "off" after three crashes; then nothing is restarted until the extension reloads. */
  readonly state: "idle" | "starting" | "ready" | "off";
  onDidChangeState(listener: () => void): void;
  dispose(): void;
}

/** The node arguments and script arguments that start the bundled server. */
export const serverArgs = (script: string) => ["--max-old-space-size=256", script, "--stdio"];
```

Behaviour, each line a test:

- The process is started by the first `sync`, not by the constructor.
- `initialize` sends `rootUri` (first folder), `workspaceFolders`, and client capabilities
  as in the spike script: `workspace.configuration`, `workspace.workspaceFolders`,
  `textDocument.semanticTokens` (`requests.full`, `formats: ["relative"]`, the standard
  type and modifier lists), `hover.contentFormat ["markdown","plaintext"]`,
  `completion.completionItem` (`snippetSupport: false`, `resolveSupport` for
  `documentation` and `detail`), `signatureHelp`, `definition.linkSupport: true`. Then
  `initialized`, then `workspace/didChangeConfiguration {settings: {}}` (cursorpyright's
  build needed that nudge before it asked for configuration; harmless for the bundled one).
- `workspace/configuration` is answered item by item: section `python` gets
  `{pythonPath: await options.pythonPath(item.scopeUri)}` (the key is left out when
  undefined); a section ending in `.analysis` gets
  `{diagnosticMode: "openFilesOnly", autoImportCompletions: false}`; anything else `{}`.
  Auto-import is off because its extra edit lands on line 0, which is outside the block.
- Documents carry `languageId: "python"` and a version that starts at 1 and rises by one
  per changed text. `didChange` sends the whole text (`contentChanges: [{text}]`).
- Calls made while the server is starting are queued in order and sent once it is ready.
- `textDocument/publishDiagnostics`, `window/logMessage` (to `log`) and unknown server
  requests are absorbed.
- When the process exits unasked, pending requests resolve `null`, and the next `sync`
  starts a new process and re-opens every view at version 1. The third unasked exit sets
  `state` to `"off"`.
- `dispose()` sends `shutdown` then `exit`, and kills the process if it has not gone after
  2 s.

## Task 5: translating tokens

**Files:** create `src/core/semantic-tokens.ts`, `test/core/semantic-tokens.test.ts`.

```ts
/** What the extension announces to the editor: standard names only, so every theme has a colour. */
export const LEGEND = {
  tokenTypes: ["namespace", "type", "class", "enum", "typeParameter", "parameter", "variable", "property", "enumMember", "function", "method", "keyword", "decorator"],
  tokenModifiers: ["declaration", "definition", "readonly", "static", "async", "defaultLibrary"],
} as const;

/** The server's token data in LEGEND's numbering, without tokens outside the body or of a type LEGEND lacks. */
export function translateTokens(data: number[], from: Legend, view: PythonView): number[];
```

Rules: `selfParameter` and `clsParameter` become `parameter` (the colour they resolve to
where cursorpyright registers them, and the only colour available where it does not);
types are matched by name, never by index, so a server whose legend is ordered differently

```ts
export function registerPythonTokens(context: vscode.ExtensionContext, blocks: PythonBlocks): void {
  const changed = new vscode.EventEmitter<void>();
  context.subscriptions.push(
    changed,
    blocks.onDidChange(() => changed.fire()),
    vscode.languages.registerDocumentSemanticTokensProvider(
      TEMPLATE_SELECTOR,
      {
        onDidChangeSemanticTokens: changed.event,
        async provideDocumentSemanticTokens(document, token) {
          const view = blocks.viewOf(document);
          const answer = view && (await blocks.server.semanticTokens(document.uri.toString(), cancelOf(token)));
          // No answer keeps the grammar's colours; an empty one would too, but would also cache.
          return answer ? new vscode.SemanticTokens(new Uint32Array(translateTokens(answer.data, answer.legend, view))) : undefined;
        },
      },
      new vscode.SemanticTokensLegend([...LEGEND.tokenTypes], [...LEGEND.tokenModifiers]),
    ),
  );
}
```

export interface CompletionEntry { label: string; kind?: number; detail?: string; documentation?: string; sortText?: string; filterText?: string; insertText?: string; replace?: Range; data?: unknown }

completion(uri: string, position: Position, trigger: string | undefined, cancel?: Cancel): Promise<{ items: CompletionEntry[]; incomplete: boolean }>;
resolveCompletion(entry: CompletionEntry, cancel?: Cancel): Promise<CompletionEntry>;
signatureHelp(uri: string, position: Position, trigger: string | undefined, retrigger: boolean, cancel?: Cancel): Promise<{ signatures: { label: string; documentation?: string; parameters: { label: string | [number, number]; documentation?: string }[] }[]; activeSignature: number; activeParameter: number } | null>;

`textEdit` (either `range` or `replace`), and **drops any item with

one anyway). `resolveCompletion` sends `completionItem/resolve` with the original `data`.

(the server's own list, read from `capabilities.completionProvider.triggerCharacters`, is
logged once so a drift is visible) and a signature help provider with `(` and `,`; both
gated by `inBody` like task 7. LSP `CompletionItemKind` minus one is
`vscode.CompletionItemKind`. Items whose replace range leaves the body are dropped.

Before answering, the adapter must make sure the server has the text the position refers
to: call `blocks.viewOf(document)` (which syncs) in the provider itself, never rely on a
change event having run first.
