## 1. Decisions

Already decided in this plan (say so if any is wrong):

1. **No language server now.** Everything M2 forwards is reached through
   `vscode.commands.executeCommand("vscode.execute…Provider")`, which only exists in the
   extension host; pjx knowledge comes from a pyjinhx subprocess. A server process would
   add a protocol and remove nothing. `src/core/` stays free of `vscode` imports so that a
   server for other editors is later a change of transport.
2. **One HTML view serves HTML, CSS and JS.** The virtual document handed to the built-in
   HTML service rewrites `{#css` to `<style>` and `{#js` to `<script>`, so `{#css`/`{#js`
   bodies, `<style>` and `<script>` all get the HTML service's embedded modes. No CSS or
   JS service is bundled.
3. **Declaring pyjinhx as an HTML language participant is rejected.** It would make the
   built-in server read raw Jinja and register its formatter for `.pjx`, which is the
   damage M0 removed.
4. **The injections into `text.html.basic` and `text.html.jinja` are dropped.** From M1
   the grammar applies to `.pjx` files and to `template = …` strings in `.py` files only.
   M0 already limited the formatter the same way.
5. **No hard-coded colours.** Component tags get `entity.name.tag.pyjinhx
   support.class.component.pyjinhx` (the convention JSX uses, so themes already colour
   it), block keywords `keyword.control.pyjinhx`.
6. **Call-site validation is not reimplemented in TypeScript.** M3 shows the diagnostics
   pyjinhx emits. Unknown tag, unknown prop, missing prop and `Literal` mismatch wait for
   pyjinhx (ask A1).
7. M1 ships as 0.3.0, one minor version per milestone after that.

Needs the maintainer (four):

- **D1 (blocks M1 task 4). Where Jinja highlighting comes from.**
  (a) Bundle wholroyd's `jinja.json` (MIT, about 170 lines) under the scope name
  `source.pyjinhx.jinja` and always use it. Same colours for everyone, one test mode,
  no extension to install. *Recommended; the plan is written for it.*
  (b) `extensionDependencies: ["wholroyd.jinja"]`: no vendored grammar, but every user
  is made to install an extension, and the tests still need a vendored copy.
  (c) Use an installed Jinja grammar when there is one and the bundled one otherwise:
  two colourings and two test modes for ever.
- **D2 (blocks M4 task 5). Does the formatter keep re-indenting HTML structure?**
  Recommended: yes, but on the shared region scanner, with its own tokenizer deleted.
  The alternative is a formatter that only applies pjx rules (slot explosion, blank line
  after the header, block bodies) and never moves an HTML line.
- **D3 (blocks M5 task 2). May the extension run `pyjinhx.stubgen` on save?** It writes
  `card.pyi` beside `card.pjx`, which is pyjinhx's documented design, but it is a write
  into the source tree. Recommended: off by default, a setting to turn it on, and a quick
  fix on the `stub-missing` / `stub-stale` diagnostics either way.
- **D4 (blocks M5 part b). If the editor's Python service will not serve a virtual
  document** (already true for cursorpyright), is a private Pyright process acceptable?
  Recommended: decide after the M5 spike; the alternative is to stop at M5 part a.

Optional maintainer action: `sudo pacman -S xorg-server-xvfb` so editor tests can run
locally without opening a window.

3. **Editor tests** (`test/editor/`, from M2). `@vscode/test-electron` downloads VS Code
   into `.vscode-test/` and runs a mocha suite inside the extension host.
   - CI: `xvfb-run -a npm run test:editor` on `ubuntu-latest` (it has `xvfb-run`).
   - This machine: there is no `xvfb-run`. Without it the run opens a real window on the
     Hyprland session, which works but is not headless. With `xorg-server-xvfb`
     installed, the CI command works locally too.
   - `PJX_EDITOR_PATH=/usr/share/cursor/cursor` runs the same suite in Cursor, which is
     the only way to test against cursorpyright. Local only.
   - What an editor test can assert: language id; completion, hover and definition
     through `vscode.execute…Provider` on a `.pjx` file; diagnostics through
     `vscode.languages.getDiagnostics`; that `editor.action.commentLine` inside a `{#css`
     body writes `/* */` (which proves `embeddedLanguages`).
   - What it cannot assert: token colours. There is no API for the tokens the editor
     computed, so highlighting is covered by layer 1 and a short manual checklist per
     release.
   - The manifest layer is tested with a fake interpreter (a script that prints a
     fixture manifest), so CI needs no Python for it. One extra CI job installs pyjinhx
     and runs the same suite against the real command.

**3. Block rules (M).** File: `syntaxes/pyjinhx.json`.
- Four rules, `meta.block.{def,css,js,python}.pyjinhx`. Opener `{#` scoped
  `punctuation.definition.block.begin.pyjinhx`, keyword `keyword.control.pyjinhx`, closer
  `punctuation.definition.block.end.pyjinhx`. The keyword touches `{#`; no `-` is
  accepted (fixes W8).
- `css`, `js`: the keyword ends its line; the opener may be indented. `python`: opener
  in column 0. `def`: followed by whitespace, the end of the line or `#}`; one line or
  several.
- Body scopes: `meta.embedded.block.css source.css`, `meta.embedded.block.js source.js`,
  `meta.embedded.block.python source.python`, each including the real grammar.
- Termination follows Jinja: the first `#}` ends the block. Use the technique Markdown
  uses for fenced code: the body is an inner `begin`/`while` rule whose `while` is
  "this line holds no `#}`", so an open CSS brace or Python string cannot swallow the
  closer; the line that holds `#}` is tokenized by the outer rule, which ends at `#}`.
  This is what the scratch run validated.
- `{#def` body includes `source.python`, plus one pjx rule before it that scopes a name
  followed by `:` as `variable.parameter.pyjinhx`.
- The legacy `{# def` header: accepted on the first line of the document only (`\A`),
  as `legacy_spaced_form.first_position_only` says.
- Keep M0's `comment.block.pyjinhx` rule after the block rules, so prose comments
  (`{# css tweaks #}`, `{#cssx`, `{#python is nice #}`) are comments.
- Tests: tasks 2's corpus and data tests pass; M0's `def-and-comments.test.ts` is
  updated for the new scope names and asserts that `padding` in a `{#css` body is
  `support.type.property-name.css`, a `{#js` body is `source.js`, a `{#python` body is
  `source.python`; new cases for a `#}` inside a CSS string, an unclosed CSS brace before
  the closer, and a triple-quoted Python string before the closer.

## 4. M2: forward language features (size L)

Result: completion, hover, signature help, definitions and colours for HTML, CSS and JS
in `.pjx` files, answered by the editor's own services.

Design:

- **Region scanner**, `src/core/regions.ts`. One pass over the text, no `vscode`
  import. Output: blocks (opener, body, closer ranges and corpus-shaped
  `open_line` / `body_lines` / `close_line`), the first error (corpus codes), Jinja
  comments, `{{ }}`, `{% %}`, raw regions, HTML comments, `<script>` / `<style>` bodies,
  and tags (name, component or not, attributes with name and value ranges). This is the
  scanner the conformance corpus was written for, and from here on the only scanner in
  the extension.
- **HTML view**, `src/core/virtual-html.ts`. Same number of lines as the source; every
  kept character keeps its line and column, so positions map by identity.
  - Jinja comments, `{% %}`, raw markers and `{#def` / `{#python` blocks become spaces.
  - `{{ … }}` becomes spaces in markup and attribute values, and an identifier-shaped
    filler of the same length inside `<script>` and `<style>`, so the JS and CSS stay
    parseable.
  - The `{#css` opener line becomes `<style>`, the `{#js` opener line `<script>`, and
    their `#}` the matching end tag. The opener ends its line by rule, so no column
    after it moves. If text follows the closer on its line, the rest of that line is
    blanked in the view; a test pins this.
  - Nothing inside a `{#css` / `{#js` body is treated as Jinja.
- **Virtual documents**, `src/vscode/virtual-documents.ts`. A
  `TextDocumentContentProvider` under the scheme `pjx-embedded`, path
  `/<encoded source uri>.html`, refreshed when the source changes.
- **Forwarding**, `src/vscode/forwarding.ts`. Providers registered for `pyjinhx` that
  call `vscode.execute…Provider` on the view and return the results. Positions that the
  view blanked are not forwarded; results pointing at the view's URI are rewritten to
  the source URI.

Limits to state in the README: JS intelligence is the HTML service's embedded mode
(one file, DOM typings, no project imports), because the TypeScript service does not
serve custom schemes. No HTML features inside slot values. No auto-closing of tags by
the HTML service (it is a private request of the built-in client); the language
configuration's pairs cover the common case.

Tasks:

1. **Editor test harness (S).** `@vscode/test-electron`, mocha, `test/editor/`,
   `npm run test:editor`, `.vscode-test/` in `.gitignore`, CI step under `xvfb-run -a`.
   First test: a `.pjx` file opens with language id `pyjinhx`.
2. **Spike, half a day, written up in `docs/plans/notes-m2-spike.md` (S).** Four editor
   tests that answer: does the HTML service answer completion and hover for a
   `pjx-embedded:` `.html` document; do its embedded CSS and JS modes answer inside
   `<style>` / `<script>` there; does anything answer for a `pjx-embedded:` `.js`
   document (expected: no); are diagnostics for the view available from
   `vscode.languages.getDiagnostics`. If the first two fail, stop and re-plan: the
   fallback is to bundle `vscode-html-languageservice` and `vscode-css-languageservice`.
3. **Region scanner (M).** Tests first: `test/core/regions-corpus.test.ts` runs all 40
   corpus cases and compares `blocks` and `error` (code and line) exactly, honouring
   `known_gap`; unit tests for tags, attributes, Jinja regions, script/style bodies,
   CRLF and BOM.
4. **HTML view (S).** Tests first: for every corpus case and every formatter fixture,
   the view has the same line count; every character that is not blanked is equal to the
   source character at the same line and column; opener and closer lines are as
   specified; fillers are the same length.
5. **Virtual document provider (S).** Editor test: the view of an open `.pjx` updates
   after an edit.
6. **Forwarding providers (M).** In this order: completion (with resolve), hover,
   signature help, definition, document highlights, colours, folding. Editor tests, one
   per language region: `<di` completes `div`; `colo` in a `{#css` body completes
   `color`; `document.` in a `{#js` body lists `getElementById`; the same inside
   `<style>` and `<script>`; no HTML completion inside a `{#python` body or a Jinja
   comment.
7. **Diagnostics from the view (S, only if the spike says they are reliable).** Mirror
   the HTML service's CSS and JS diagnostics onto the source, dropping any that touch a
   filler. Off by default behind `pyjinhx.validate.embedded`.
8. **Swap callers to the scanner (S).** `src/core/def-header.ts` is deleted;
   `diagnostics.ts` uses the scanner. README and CHANGELOG. Version 0.4.0.

## 5. M3: the thin pjx layer, driven by the manifest (size M–L)

Result: component tags and props complete, hover, go to definition and diagnostics, all
read from `python -m pyjinhx.manifest`. The `existsSync` heuristic is gone.

Design:

- **Interpreter discovery**, `src/vscode/python-env.ts`, in this order: the setting
  `pyjinhx.pythonPath`; the Python extension's API
  (`ms-python.python` → `environments.getActiveEnvironmentPath(folder)`, and its change
  event), used if installed and never declared as a dependency; `.venv/bin/python` (or
  `Scripts/python.exe`) in the workspace folder; `python3` on `PATH`.
- **Manifest service**, `src/vscode/manifest-service.ts`. Per workspace folder:
  `python -m pyjinhx.manifest <folder>` on activation; again, debounced 300 ms, when a
  `.pjx`, `.py` or `.pyi` file is saved, created or deleted. One run at a time; a newer
  request kills the older process; 10 s timeout. For the active dirty document,
  `--stdin --filename` debounced 250 ms, and its components and diagnostics replace
  those of that path in the cached manifest. Extra paths and `--sys-path` come from the
  settings `pyjinhx.manifest.paths` and `pyjinhx.manifest.sysPath` (both empty by
  default).
- **Reader**, `src/core/manifest.ts`. Types for manifest version 1; unknown keys are
  ignored; another `manifest_version` puts the extension in limited mode with one
  message. Lines are converted from 1-based to 0-based; columns are already UTF-16.
  Indexes by tag and by path.
- **Custom data**, `src/core/custom-data.ts`. The manifest becomes HTML custom data
  (tags with a description, attributes with `annotation = default`, `values` from
  `literal_values`, boolean props as valueless attributes). It is given to an in-process
  `vscode-html-languageservice` created with only this provider
  (`useDefaultDataProvider: false`), run on the M2 HTML view. The real HTML completion
  engine then decides whether the cursor is in a tag name, an attribute name or a value.
  Its results are merged with the forwarded ones. The built-in HTML server cannot be
  given custom data at run time without editing the user's settings, which this
  extension will not do.
- **Workspace trust.** `capabilities.untrustedWorkspaces: "limited"`: in an untrusted
  workspace no interpreter is run; highlighting, M2 forwarding and the fallback index
  still work. `capabilities.virtualWorkspaces: false`.
- **Fallback when pyjinhx is not importable, too old, or the workspace is untrusted.**
  An index built in TypeScript from the workspace's `.pjx` files: tag from the file name,
  prop names from the `{#def` header through the region scanner. Tag completion and go
  to definition work; no hover details, no diagnostics. A status bar item says
  "pyjinhx: limited" and its tooltip says why and how to fix it.

## 8. Asks of pyjinhx (delta against PR #1075 as built)

Already there and used by this plan: static manifest with versions, components of all
four kinds, props with `literal_values` / `slot` / `children` / ranges, members, block
lines, `has_stale_def_header`, diagnostics with codes, `--stdin --filename`,
`--sys-path`, `--grammar`, the block grammar as data, the corpus, line-preserving stubs.

Still missing, most useful first:

- **A1. Call-site checking.** The manifest describes components but not their uses.
  Unknown tag, unknown prop, missing required prop and a `Literal` value that is not
  allowed cannot be reported without re-implementing pyjinhx's rules in TypeScript.
  Ask: the manifest emits them as diagnostics (codes such as `unknown-component`,
  `unknown-prop`, `missing-prop`, `invalid-literal`), in both the path and `--stdin`
  modes. Blocks nothing; it is what makes M3's diagnostics worth having.
- **A2. Inherited props.** `bases` is names only, and a subclass's inherited fields are
  not in `props`, so completion is incomplete for it. Ask: resolve bases that are in the
  scanned set, and set a flag such as `props_complete: false` when a base could not be
  resolved, so the editor (and A1) can stay quiet there.
- **A3. Text for hover.** No docstring for a class, no description for a prop
  (`Field(description=…)`), no signature or return annotation for a member. Hover can
  show only `annotation = default` today.
- **A4. The corpus is not in the package.** It lives in `tests/fixtures/`, so vendoring
  needs a repository checkout at a ref. Ask: ship it as package data (or in the sdist)
  and tag releases, so `sync-pyjinhx` can pin to `pyjinhx_version`. Three cases to add:
  the legacy `{# def` header in first position (the only positive case of
  `legacy_spaced_form`), `{#def` followed directly by `#}` or the end of the line
  (`after_keyword: whitespace_or_end`), and a block inside a `template = r"""` string.
- **A5. A stub without a file.** `stubgen` only writes beside the `.pjx`. Ask:
  `python -m pyjinhx.stubgen --stdin --filename F` printing the stub, for unsaved
  buffers and for M5 part b.
- **A6. One sentence in the docs.** For kind `py-template`, say that `blocks` lines and
  diagnostics are lines of the `.py` file (the code suggests so; the docs do not say).

Not asked for: an incremental or watch mode (0.14 s for 81 components is fast enough),
a JSON Schema, or anything that imports the application.
